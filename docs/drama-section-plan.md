# 短剧栏目 · 开发计划

目标：在电影之后新增第 5 个栏目「短剧」，一部剧一张卡，点进去看选集。
现有的短视频 / 长视频 / ASMR / 电影四个栏目不改行为，只增加入口、增加一个板块类型。

## 1. 现状（已核实）

### 1.1 板块模型

| 层 | 现状 |
| --- | --- |
| 客户端栏目 | `MediaSurface`：`SHORT` 短视频、`LONG` 长视频、`ASMR`、`MOVIE` |
| 媒体源板块 | `LibrarySection`：`FEED`（短视频/长视频共用）、`ASMR`、`MOVIE` |
| 时长拆分 | 服务端按 `duration_boundary_seconds`（默认 180 秒）在 `/api/feed?category=short|long` 里切分 |

所以「4 个栏目 / 3 种来源」的判断是对的：短视频和长视频共用 `feed` 源，只是查询时按时长过滤。
新增短剧 = 新增第 4 种来源板块 + 第 5 个栏目，不动 `feed`/`asmr`/`movie` 的扫描与匹配逻辑。

### 1.2 片源

`F:\nanobot-portable\shared\workspace\91crdj` 实测（2026-09-18 快照，下载器仍在跑，数量会涨）：

```
91crdj/<分类>/<剧名> [91crdj-<id>]/<剧名> 第N集 [91crdj-<id>-N].mp4
短剧 22 部 / 64 集    漫剧 9 部 / 36 集
真人剧 6 部 / 25 集   视频 6 部 / 6 集
合计 43 部 / 131 集 / 12.0 GB
命名合规率：文件夹 43/43 带 [91crdj-<id>]，文件 131/131 带 第N集
扩展名：131 个全部是 .mp4，没有杂项文件，没有未下完的 .pending
```

目录命名规整是这套方案最有利的一点：**剧集分组和排序都不需要猜，直接从名字里取。**

云端落点已经存在但为空：AList `https://guangya.deepfuck.you` 的 `/光鸭/下载器/CR短剧`。

### 1.3 元数据来源

91crdj 详情页自带：

- `og:image`：竖版海报，实测 480×720
- 标题、`共 N 集`、简介、标签、片长

取一张海报 = 一次 HTTP GET，可以只在新剧入库时取一次并永久缓存在库里。

### 1.4 已发现的一处数据问题

43 部里有 **8 部**的目录名是 `▶ 立即观看 [91crdj-xxxx]`，也就是说下载器在列表页抓到了播放按钮的文字，没抓到真正的剧名：

```
短剧/▶ 立即观看 [91crdj-1192]   短剧/▶ 立即观看 [91crdj-1343]
短剧/▶ 立即观看 [91crdj-1542]   短剧/▶ 立即观看 [91crdj-1575]
短剧/▶ 立即观看 [91crdj-1825]   漫剧/▶ 立即观看 [91crdj-1301]
漫剧/▶ 立即观看 [91crdj-1345]   漫剧/▶ 立即观看 [91crdj-1355]
```

这 8 部的目录名里都带 `[91crdj-<id>]`，所以**剧名可以用和封面同一套机制补回来**：
扫描时遇到 `▶ 立即观看` 这类占位剧名，就按 code 去详情页取一次真实标题。
同一部剧只修正一次，修正结果落库，不重复请求。

## 2. 数据模型

只在 `app/database.py` 增加一张表和一个可空外键列，不动 `movies`。

```sql
CREATE TABLE IF NOT EXISTS dramas (
    id            TEXT PRIMARY KEY,     -- source + folder 的稳定哈希
    source        TEXT NOT NULL,
    root_path     TEXT NOT NULL,
    folder        TEXT NOT NULL,        -- 相对 root 的剧集目录
    title         TEXT NOT NULL,        -- 去掉 [91crdj-xxx] 后的剧名
    code          TEXT,                 -- 91crdj-<id>
    poster_url    TEXT,
    synopsis      TEXT,
    tags          TEXT,
    episode_count INTEGER NOT NULL DEFAULT 0,
    updated_at    TEXT NOT NULL,
    UNIQUE(source, folder)
);

-- 集是真实可播放的媒体，直接复用 videos，播放/进度/预取全部白拿
ALTER TABLE videos ADD COLUMN series_id TEXT;   -- 仅短剧集有值
CREATE INDEX IF NOT EXISTS idx_videos_series ON videos(series_id, id);
```

关键取舍：**不新建 `drama_episodes` 表**。分集就是视频文件，放进 `videos` 后现有的
`/api/videos/{id}/play`、播放进度、预取、缓存 key 全部直接可用，这是最轻的做法。
`series_id` 是可空列，老库原地升级，不影响任何已有查询。

## 3. 扫描

新增 `scan_mode = "series"`（与 `tree`、`authors_recursive` 并列）。

1. 用现有 `tree` 递归走一遍，拿到全部文件（复用现成的断点续扫、跳目录、限流）。
2. 只保留可播放容器（复用 `PLAYABLE_EXTENSIONS`），丢弃 `.pending.mp4` 等未下完的中间文件。
3. 按「剧集目录」聚合成 `dramas` 行：
   - 剧名 = 目录名去掉 `[91crdj-<id>]` 后缀
   - `code` = 目录名里的 `[91crdj-<id>]`
   - 集号 = 文件名里的 `第N集`，取不到时退回文件名自然排序
   - `episode_count` = 入库集数
4. 扫描完成后同一事务内回写 `videos.series_id`，并软删除已消失的剧集行（沿用现有 `hide_videos`）。

沿用现有约定：**只在用户手动点扫描时跑，绝不自动触发。**

## 4. 封面策略

按优先级三级，前一级命中就不做下一级：

1. **目录侧的 `poster.jpg` / `cover.jpg` / `folder.jpg`**（由下载器在下载时写入）。
   零抓取、零延迟、跟着 AList 走，属于最理想的一级。
2. **91crdj 详情页 `og:image`**：仅当目录名带 `[91crdj-<id>]` 且库里还没封面时取一次并写库。
   一次一部剧，不重复抓，不参与每次扫描。
3. **没有封面** —— 卡片显示剧名文字，并且**排在有封面的剧之后**（沿用电影墙已有策略）。

第 2 级是唯一的外部请求，边界很硬：只在新剧入库时发生，缓存落库，重扫不重抓。
如果希望连这一次也不要，把第 2 级关掉即可，方案仍然完整。

## 5. 服务端接口

镜像电影的写法，新增：

| 接口 | 作用 |
| --- | --- |
| `GET /api/dramas?q=&sort=&limit=&offset=` | 剧集墙：`{items, total, nextOffset, scan}` |
| `GET /api/dramas/{drama_id}` | 详情：剧集信息 + 有序分集列表（含各自 playUrl / 时长 / 进度） |
| `GET /api/dramas/{drama_id}/poster` | 海报，走现有 `_proxy_movie_image` 同款代理与 `ETag` |

播放和续播直接复用 `/api/videos/{video_id}/play` 与现有进度接口，不新增。

## 6. 客户端（Android）

- `MediaSurface` 增加 `DRAMA("drama", "短剧")`，排在 `MOVIE` 之后；`LibrarySection` 增加 `DRAMA`。
- 新建 `ui/DramaScreen.kt`：
  - **剧集墙**：自适应列宽的海报卡（2:3），右下角 `N 集` 角标，无封面时退化为剧名卡。
  - **详情页**：整屏竖版海报打底 + 下半部分渐变压暗 + 信息层浮在上面（与电影详情页同一套语言）；
    信息区显示剧名、分类标签、`共 N 集 · X GB`、简介，然后是**选集宫格**（5 列数字按钮，已看过的集数打勾）。
  - **继续观看**：详情页顶部一个 `继续观看 第X集` 主按钮。
- 播放复用现有 `PlaybackEngine`；分集**播完自动下一集**（沿用 ASMR 的续播逻辑），手势、横屏、后台播放按钮与长视频/ASMR 完全一致。

## 7. 配置与媒体库管理

- `MediaSourceRequest.section` 的 `Literal` 增加 `"drama"`；`normalize_source_payload` 里 `drama` 默认 `scan_mode = "series"`，并拒绝 `tree` / `authors_*`。
- `LibrarySection` 增加 `DRAMA("drama", "短剧")`，`usesTreeScan` 保持现有语义（短剧走 `series`）。
- 媒体源卡片显示：剧集数 + 集数总量（复用现有 `videos` / `bytes` 字段）。

## 8. 两处排版重设计

### 8.1 电影区头部（片库信息 / 搜索 / 排序）

现状 `MovieScreen.kt` 234-305：

- 「片库 + 数字」被压进 62dp 固定宽度的 Column，数字一长就换行；
- 搜索框与它挤在同一行，右侧没有留排序入口；
- 排序是两个 pill 按钮独占一行，加上搜索行共两行，垂直空间被吃满。

改造为两行、每行模块都有明确最小高度：

```
第 1 行  [ 搜索框（自适应，最小 48dp） ] [ 排序图标按钮 48×48 ]
第 2 行  [ 片库 2153 ] [ 已匹配 1328 ] [ 当前 24 ]   ← 36dp 高的小 chip，横向可滚动
```

- 排序不再占一行：点图标弹出底部弹层，`封面优先 / 标题` 变成带勾选的列表项。
- 统计数字从「片库」旁边挪到第 2 行的 chip，各自有固定内边距，不再被压缩换行。
- 左右统一 12dp 间距，行间距 8dp。

### 8.2 管理页 · 新增/编辑媒体源（`MediaSourceDialog`）

现状 `ManagementScreen.kt` 514 起：8 个字段纵向堆叠、全部是整行文字标签，「归属板块」用横向按钮组，加一个板块就会挤压换行（之前已经出过一次文字窜行）。

改造为全高底部弹层 + 图标化 + 分组：

```
┌ 新增媒体源                                    ✕ ┐
│ ① 归属板块                                      │
│   [▶ 视频] [🎧 ASMR] [🎬 电影] [📺 短剧]        │  ← 四个等宽方块，图标 + 3 字以内标签
│                                                 │
│ ② 基础                                          │
│   🏷  名称        <输入>                        │
│   🔗  服务地址    <输入>                        │
│   📁  根目录      <输入>                        │
│                                                 │
│ ③ 鉴权                                          │
│   🌐  匿名访问    <开关>                        │
│   🔑  令牌 / 👤 用户名 / 🔒 密码  <输入，可切换明文> │
└─────────────────────────────────────────────────┘
```

- 板块选择改成 4 个等宽图标块，标签固定不超过 3 字，加板块时不再挤压换行。
- 字段用前置图标 + 占位符代替整行文字标签，行高 48dp，用分隔线代替间距，信息密度更高。
- 全部图标沿用现有线性图标风格（透明底、白色线条），与播放器控制层保持一致。
- 保存/取消固定在弹层底部，不随滚动走。

## 9. 实施顺序

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| 1 | 上传 `CR短剧` 到 AList，建 `drama` 源 | 服务端能列出目录树 |
| 2 | 数据模型 + 扫描器 + 单测 | 43 部剧 / 131 集入库；重复扫描不产生重复行；`.pending` 被忽略 |
| 3 | 接口 + 封面三级策略 | 剧集墙能出图；重扫不重复抓封面；断源后剧集保持可见 |
| 4 | Android 栏目 + 剧集墙 + 详情 + 选集 + 自动续播 | 真机：进入栏目即出列表，点集即播，播完自动下一集 |
| 5 | 管理页板块选项 | 新增/编辑/删除短剧源与其余板块行为一致 |
| 6 | 8.1 / 8.2 两处排版 | 真机竖屏不漏字、不换行、触控区 ≥48dp |

阶段 2-3 全部有单测覆盖（`tests/test_drama_scan.py`、`tests/test_drama_api.py`）。
每次发布仍走现有流程：构建 APK → 服务端 manifest + GitHub release 双通道。
